# Архитектура

Приложение `sheremetevo-app` — один процесс на C++17, построенный на GStreamer и
NVIDIA DeepStream 9.0. Всё декодирование, масштабирование, детекция и трекинг идут
на GPU, на CPU остаются перевод пикселей в координаты и отправка по UDP
(в отдельном потоке).

## Конвейер

```
 камера 0: source-bin-0 ─┐
 камера 1: source-bin-1 ─┤
   ...                   ├─► nvstreammux ─► nvinfer (YOLO26) ─► [nvtracker] ─┬─► nvstreamdemux ─┬─► queue ─► nvdsosd ─► sink-bin-0 ─► RTSP
 камера N: source-bin-N ─┘   (пачка из N                                     │                   └─► ...   (по ветке на камеру)
                              кадров)                                         │
                                                                              └─ проба: пиксели → WGS84 ─► PointsSender (поток) ─► UDP, protobuf
```

`source-bin-<N>` (одна на камеру, `custom_bins.cpp`):

```
rtspsrc ─► rtph264depay ─► nvv4l2decoder ─► [nvvideoconvert flip-method] ─► [RGBA ─► nvdewarper ─► nvvideoconvert ─► NV12]
```

- Поддерживаются только потоки H.264. Декодер работает с `disable-dpb` и
  `low-latency-mode`, поэтому поток должен быть без B-кадров.
- Поворот (`flip-method`) и выпрямление (`dewarper-config`) добавляются в цепочку,
  только если заданы в группе камеры в `app.ini`. Без них декодер подключается к
  `nvstreammux` напрямую.
- `nvstreammux` приводит все кадры к размеру `frame-width` × `frame-height` и
  собирает из них пачку. Если камера отстала больше чем на `batched-push-timeout-us`,
  пачка уходит без неё, остальные камеры не ждут.

Дальше по конвейеру:

- `nvinfer` — детектор YOLO26, конфиг в `configs/config_infer_primary_yolo.txt`
  (см. [model.md](model.md)). Оставлен только класс 4 COCO — `airplane`.
- `nvtracker` — необязательный трекер, даёт объектам постоянный `object_id`.
  Без него `object_id` в сообщениях равен -1.
- На выходе последнего элемента анализа (трекера, если он включён, иначе `nvinfer`)
  стоит проба `pgie_src_pad_buffer_probe` (`probers.cpp`), которая считает координаты
  и отправляет сообщения.
- Видеовыход (`[output] enabled=true`): `nvstreamdemux` разбирает пачку обратно по
  камерам, `nvdsosd` рисует рамки, id трека, точку и координаты, `sink-bin-<N>`
  кодирует в H.264 (`nvv4l2h264enc`) и публикует поток на RTSP-сервер
  (`rtspclientsink`) по адресу `<uri-prefix>_<N>`. Перед `nvdsosd` стоит очередь,
  которая выбрасывает старые кадры, поэтому медленный RTSP-сервер не тормозит
  детекцию. Ветки собирает и перезапускает `output_manager.cpp` (см. «Устойчивость»).
  При `enabled=false` вместо всей ветки стоит `fakesink`.

Граф реального конвейера можно получить командой `make gen-graph` (запускает
приложение с `GST_DEBUG_DUMP_DOT_DIR=graphs`, после остановки появится
`graphs/sheremetevo.dot`) и `make graph` (рисует `graphs/sheremetevo.png`, нужен graphviz).

## Обработка кадра

Для каждого кадра пачки проба:

1. Определяет камеру по `pad_index` (номер входа `nvstreammux`). Он совпадает с
   номером группы `[cameraN]` и задаёт `camera_id` и калибровку.
2. Отбрасывает объекты, у которых ширина рамки, делённая на высоту, не больше
   `[geo] min-aspect-ratio`. Самолёт в профиль или анфас с крыльями шире, чем выше;
   так отсекаются ложные срабатывания на вертикальных объектах.
3. Берёт точку касания с землёй — середину нижней стороны рамки — и переводит её в
   (долгота, широта) по гомографии камеры (`PixelGeoTransformer`, см.
   [calibration.md](calibration.md)).
4. Передаёт объекты кадра в `PointsSender` (`points_sender.cpp`) и сразу
   возвращается. Кадр передаётся, даже если объектов нет. `PointsSender` в отдельном
   потоке копит кадры `[udp] batch-interval-ms` и отправляет их по UDP пачками
   protobuf `Batch` не больше `max-datagram-bytes` (см. [output-format.md](output-format.md)).
5. Добавляет разметку для видеовыхода.

Время кадра берётся из `ntp_timestamp`, которое проставляет `nvstreammux`
(по умолчанию — системное время прихода кадра), в секундах Unix-эпохи.

## Устойчивость

- **Переподключение камер** (`source_manager.cpp`). Камера перезапускается, если внутри
  её `source-bin` возникла ошибка (обрыв связи, сервер недоступен) или от неё нет кадров
  дольше `[rtsp] stall-timeout-sec`. Bin камеры переводится в `NULL` и через
  `reconnect-interval-sec` запускается снова. EOS от сервера камеры в `nvstreammux`
  не пропускается, иначе камера считалась бы законченной навсегда. Номер камеры при
  перезапуске не меняется, калибровка остаётся прежней. Проверка идёт раз в секунду.
- **Изоляция видеовыхода** (`output_manager.cpp`). Видеовыход вспомогательный, его сбой
  не останавливает анализ и отправку точек. Кадр в ветку передаёт проба на выходе
  `nvstreamdemux` (`gst_pad_chain`), и ошибка потока из ветки (`rtspclientsink` не
  смог отправить) до `nvstreamdemux` не доходит. ERROR с шины изнутри ветки
  останавливает только её (элементы ветки переводятся в `NULL`, кадры для неё
  отбрасываются), а таймер запускает её снова. Пауза растёт от
  `[rtsp] reconnect-interval-sec` вдвое до 60 с.
- **Прочие ошибки** (nvinfer, трекер, nvstreammux) завершают приложение с кодом 1.
  Перезапуск процесса — задача среды развёртывания (см. [deploy.md](deploy.md)).
- **Остановка.** Первый `SIGINT`/`SIGTERM` отправляет EOS в конвейер, чтобы закрыть
  энкодеры и RTSP-сессии. Если EOS не дошёл за 3 с, приложение выходит всё равно.
  Повторный сигнал — немедленный выход. Перевод конвейера в `NULL` ограничен 10 с
  (`alarm`).
- **Проверки при старте.** Конфиг и все калибровки загружаются и проверяются до
  подключения к камерам: ошибка в `app.ini` или CSV видна сразу.

## Журнал

Журнал ведёт `log.cpp`: у каждой строки есть время, уровень и компонент, у записей
про камеру ещё и номер камеры. `debug`/`info` идут в stdout, `warning`/`error` — в
stderr, можно дописывать в файл с ротацией и переключить формат на JSON (`[logging]`).
Сообщения через `g_print`/`g_printerr` тоже попадают в журнал. Формат записей и
список компонентов — [monitoring.md](monitoring.md).

Метрики Prometheus отдаёт `metrics.cpp` (`[metrics]`): страница собирается в главном
цикле раз в секунду, отдельный поток только раздаёт готовый текст.

## Исходники

| Файл | Назначение |
| :--- | :--- |
| `main.cpp` | Загрузка конфига и калибровок, сборка конвейера, сигналы, главный цикл |
| `app_config.cpp/.hpp` | Разбор `app.ini` (GKeyFile) и CSV калибровки |
| `custom_bins.cpp/.hpp` | `source-bin` камеры (RTSP, декодер, поворот, nvdewarper) и `sink-bin` видеовыхода |
| `callbacks.cpp/.hpp` | Подключение динамических падов `rtspsrc` к депакетайзеру |
| `source_manager.cpp/.hpp` | Сторож камер: обнаружение зависания, переподключение, EOS при остановке |
| `output_manager.cpp/.hpp` | Ветки видеовыхода: сборка, изоляция ошибок от анализа, перезапуск |
| `health.cpp/.hpp` | Heartbeat-файл для Docker HEALTHCHECK, сторож зависания главного цикла и отсутствия кадров |
| `log.cpp/.hpp` | Журнал: уровни, компоненты, формат text/json, файл с ротацией, перехват `g_print` |
| `metrics.cpp/.hpp` | HTTP-эндпоинт `/metrics` в формате Prometheus |
| `bus_call.cpp/.hpp` | Обработка сообщений шины: ошибки камер — в переподключение, видеовыхода — в перезапуск ветки, остальные — выход |
| `probers.cpp/.hpp` | Проба: фильтр рамок, перевод в координаты, передача в `PointsSender`, разметка, статистика |
| `pixel_transformer.cpp/.hpp` | Гомография пиксели → WGS84 в локальной метрической системе |
| `message.hpp` | Структура результата кадра внутри приложения |
| `points_sender.cpp/.hpp` | Накопление кадров, сериализация в protobuf, нарезка на датаграммы, отправка в отдельном потоке |
| `proto/points.proto` | Схема UDP-сообщений; C++-код генерируется при сборке в `build/gen/` |
| `udp_connection.cpp/.hpp` | UDP-сокет к получателю |
| `tools/udp_receiver.py` | Отладочный приёмник UDP-сообщений |
